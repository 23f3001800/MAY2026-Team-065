# Frontend ↔ API Integration Reference

What the React frontend calls, what it gets back, and what the backend offers
that we have not wired yet.

**Status of this document**

- Written against `origin/develop` — that is what the frontend currently targets.
- The AI and notification-management endpoints in [Part 3](#part-3--available-on-rajabackend-not-yet-on-develop)
  exist **only on `raja_backend`** (`89d9377`). They are not merged, so nothing
  in the app uses them yet. Do not build against them until that branch lands.
- Generated by reading `backend/main.py`, `backend/schemas.py` and raja's
  `backend/openapi.yaml`. Raja's file is the authority; this one is the
  frontend's view of it.

Base URL comes from `REACT_APP_API_URL`, default `http://localhost:8000`.
**No `/api` prefix** — routes are mounted at the root.

---

## How requests are made

Everything goes through [`src/api/client.js`](../src/api/client.js):

- Attaches `Authorization: Bearer <token>` from `localStorage`.
- Serialises a plain object as JSON, a `URLSearchParams` as form-encoded, and a
  `FormData` as multipart — **without** setting `Content-Type` for the last one,
  because the browser must choose the boundary itself.
- Normalises FastAPI's two error shapes: `detail` is a string for
  `HTTPException` but an array of `{loc, msg}` objects for 422s.
- On `401`: clears the session and hard-redirects to `/login?expired=1`, then
  throws `SessionExpiredError`. Callers should ignore that error rather than
  render it — the user is already gone.

Wire-format translation lives in [`src/api/mappers.js`](../src/api/mappers.js).
No page component ever sees a `SCREAMING_CASE` enum or a raw `categoryId`.

## Part 1 — Endpoints the frontend uses today

### Auth

| | |
|---|---|
| **`POST /auth/login`** | `src/api/auth.js` → Login page |

Request is **form-urlencoded, not JSON** (`OAuth2PasswordRequestForm`):

```
username=<email>&password=<password>
```

Response is only `{ access_token, token_type }` — **there is no user object**.
Identity is decoded from the JWT payload (`sub` = email, `userId`, `role`)
client-side. That is display and routing data only; the backend re-verifies the
signature on every request, so a tampered payload gains nothing.

| | |
|---|---|
| **`POST /auth/register`** | `src/api/auth.js` → Register page |

```jsonc
{ "userId": "…", "name": "…", "email": "…", "phone": "…",
  "password": "…", "role": "citizen", "address": "…" }
```

`userId` is **required by the schema but discarded** — the endpoint generates
its own UUID. Omitting it is a 422. Only `role: "citizen"` is accepted; anything
else is a 400.

### Complaints

| Endpoint | Used by |
|---|---|
| `POST /complaints/` | Report Issue |
| `GET /complaints/` | My Complaints, Officer/Admin queue |
| `GET /complaints/{id}` | Complaint Details |
| `GET /complaints/nearby` | Nearby Issues |
| `GET /complaints/worker/tasks` | Worker Tasks |
| `POST /complaints/{id}/image` | Report Issue, Worker evidence |
| `PATCH /complaints/{id}/assign` | Officer drawer |
| `PATCH /complaints/{id}/status` | Officer drawer, Worker drawer |
| `PATCH /complaints/{id}/category` | Officer drawer |
| `POST /complaints/{id}/feedback` | Complaint Details |

**Create** — citizen only. Note the nested location and the **mandatory
coordinates**:

```jsonc
{
  "description": "…",
  "categoryId": "CAT-ROA-01",
  "location": { "latitude": 12.97, "longitude": 77.59, "address": "MG Road" }
}
```

Because `latitude`/`longitude` are required floats, Report Issue asks for
browser geolocation on mount and blocks submit without it.

**`ComplaintResponse`** (what every complaint endpoint returns):

```jsonc
{
  "complaintId": "CMP-A1B2C3",
  "description": "…",
  "status": "PENDING",          // PENDING | ASSIGNED | RESOLVED | REJECTED
  "severity": "LOW",            // LOW | MEDIUM | HIGH | CRITICAL
  "createdAt": "…", "updatedAt": "…",
  "location": { "locationId": 4, "latitude": 0, "longitude": 0, "address": "…" },
  "category": { "categoryId": "…", "name": "…", "department": "…" }
}
```

There is **no title, no assigned worker, no status history, no media, and no
feedback** on this response. See [Part 2](#part-2--gaps-the-ui-works-around).

**Listing is role-scoped server-side.** Citizens get their own complaints;
officers and administrators get all of them; field workers get a 403 and must
use `/complaints/worker/tasks` instead.

**Image upload** is a *separate second request* after create, multipart, field
name literally `file`. The two are not in one transaction, so Report Issue
reports "complaint filed, photo failed" as its own outcome.

**Assign** takes `{ "fieldWorkerId": "…" }` and will **400 on a skill
mismatch**: the backend requires the complaint category's `department` to be a
substring of the worker's `skillSet`. A worker whose skillSet reads `"Plumbing"`
cannot take a `"Water & Plumbing"` complaint. The officer drawer pre-checks this
so the officer sees a reason instead of an error.

**Status** takes `{ "status": <StatusEnum>, "remarks": "…" }`. Changing status
writes a `StatusHistory` row and fires a notification to the citizen.

**Feedback** takes `{ "rating": 1-5, "comments": "…" }` and is rejected unless
the complaint is `RESOLVED` and belongs to the caller.

### Workers

| Endpoint | Notes |
|---|---|
| `GET /workers/?skillSet=` | Officer/admin only. `skillSet` filter is an ILIKE match. |
| `POST /workers/` | Admin only. |
| `PATCH /workers/me/availability` | Field worker only. `{"status": "AVAILABLE" \| "UNAVAILABLE"}` — no other value passes the pattern. |

`FieldWorkerResponse` is `{ userId, name, phone, skillSet, availabilityStatus }`.
No task count, so the UI shows "unknown" rather than a misleading `0`.

### Admin

| Endpoint | Notes |
|---|---|
| `GET /admin/analytics` | Returns `{ overview: { totalComplaints }, breakdownByStatus, breakdownBySeverity }`. |
| `GET /admin/users?query=&role=&skip=&limit=` | `limit` max 100. Returns polymorphic user rows — `department`/`skillSet` appear only on officer/worker rows. |
| `POST /admin/users/official` | Creates an officer. |
| `PATCH /admin/users/{user_id}` | Changing `role` is rejected with a 400 by design. |
| `PATCH /users/{userId}/reset-password` | Admin only. Note this is **not** under `/admin`. |

### Notifications

`GET /notifications/me` — citizen only; other roles get 403.
Returns `{ notificationId, message, type, sentAt, isRead, complaintId }`.

## Part 2 — Gaps the UI works around

These are missing backend capability on `develop`, not translation problems.
Each one has a visible consequence, so please do not "fix" the UI without
fixing the endpoint first.

| Missing | What the UI does instead |
|---|---|
| No `IN_PROGRESS` / `CLOSED` in `StatusEnum` | `toApiStatus()` returns `null` for them so they can never be sent. They are display-only. |
| No `GET /categories` | `CATEGORIES` in `mappers.js` is a **hand-maintained mirror of `backend/seed.py`**. Edit both together or the app writes invalid category ids. |
| No status-history endpoint | Complaint Details shows only reported/updated, with a note explaining why. |
| No media read endpoint | Uploaded photos cannot be displayed back. `PhotoTile` renders a placeholder, never an `<img>`. |
| No feedback read endpoint | A rating cannot be shown after reload, and submitting twice creates two rows. |
| No mark-notification-read endpoint | Read state is client-side and resets on reload. |
| No AI classification or duplicate detection | Those panels say "not available" rather than showing invented confidence scores. |
| No title field on a complaint | List views derive one from the first sentence of the description. |
| `/complaints/nearby` returns no distance | Distance is computed client-side with a haversine over the returned coordinates. |

## Part 3 — Available on `raja_backend`, not yet on `develop`

**Do not wire these up yet.** They are documented so the work can be planned.
Once `raja_backend` merges, most of Part 2 disappears.

### Notification management — closes three gaps

| Endpoint | Unlocks |
|---|---|
| `PATCH /notifications/{id}/read` `{isRead}` | Persistent read state |
| `POST /notifications/me/read-all` → `{message, updated}` | Real "mark all as read" |
| `GET /notifications/me/unread-count` → `{unread}` | Sidebar badge without loading the list |
| `DELETE /notifications/{id}` | Dismissing a notification |

`GET /notifications/me` also gains `unreadOnly`, `type`, `skip`, `limit` query
params, so the Unread filter can move server-side. `NotificationResponse` gains
`recipientId`, `readAt` and `priority` — priority would let the list colour-code
rather than inferring urgency from the message text.

### AI endpoints

| Endpoint | Request | Response |
|---|---|---|
| `GET /ai/health` | — | availability probe |
| `POST /ai/categorize` | `{description}` | `{suggestions[], source}` |
| `POST /ai/severity` | `{description, categoryId}` | `{severity, confidence, reason, signals[], source}` |
| `POST /ai/duplicates` | `{description, categoryId, latitude, longitude}` | `{isDuplicate, candidates[], source}` |
| `POST /ai/triage` | `{description, categoryId?, latitude?, longitude?}` | `{category, severity, duplicates, summary, vision, source}` |
| `POST /ai/analyze-image` | multipart image | `{available, description, categoryId, severity, confidence, observations[], source}` |
| `POST /ai/describe` | `{description, categoryId}` | `{original, rewritten, source}` |
| `POST /ai/assistant/query` | `{question}` | `{answer, citations[], source, contextUsed}` |
| `POST /ai/complaints/{id}/analyze` | — | `TriageResponse` |

Useful nested shapes:

- `CategorySuggestionResponse` — `{categoryId, name, department, confidence, reason}`
- `DuplicateCandidateResponse` — `{complaintId, similarity, distanceKm, status, description, createdAt, reason}`

Both carry a **`reason`** string, which matters: the AI panels should show *why*
something was flagged, not just a number. And every response carries `source`,
so the UI can distinguish a deterministic rule-engine result from a model call —
worth surfacing, since users trust those differently.

`VisionResponse` has `available` plus `unavailableReason`, so the image-analysis
UI needs a genuine "AI is switched off" state rather than treating absence as
failure.

### `ComplaintResponse` gains AI fields

```
aiSuggestedCategoryId, aiSeverity, aiConfidence, aiSummary,
aiSource, aiAnalyzedAt, duplicateOfComplaintId
```

This is the big one for the officer queue. The drawer currently says
"AI Assistance — not available"; once these land it can show the suggested
category with its confidence, flag `duplicateOfComplaintId`, and let an officer
accept or override the suggestion. `fromApiComplaint()` in `mappers.js` will
need to carry these through — it currently drops them.

## Conventions worth keeping

- **Trailing slashes matter** on collections: `/complaints/`, `/workers/`.
  Without them FastAPI issues a 307 redirect.
- Keep enum and role translation **in `mappers.js`**. If a `SCREAMING_CASE`
  value reaches a component, the boundary has leaked.
- Never send a UI-only status. `toApiStatus()` returning `null` is the guard;
  respect it rather than working around it.
- When the backend cannot do something, **say so in the UI**. Every "not
  available" note in this app is deliberate and traceable to a row in Part 2.
